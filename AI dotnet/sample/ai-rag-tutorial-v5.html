Retrieval-Augmented Generation

Give a language model an open-book exam instead of a closed-book one. RAG fetches the right facts from your own documents at question time and hands them to the model before it answers.

What RAG is, and the problem it solves

Learning objectives:

  • Explain what Retrieval-Augmented Generation does in one sentence.
  • Describe why plain LLMs hallucinate on private or fresh data.
  • Name the four stages of a RAG pipeline.

A large language model learns from a fixed snapshot of text taken before its training cutoff. It has no memory of your company wiki, last night's support tickets, or a PDF you uploaded a minute ago. Ask it about those and it will often hallucinate — produce a fluent, confident answer that is simply invented, because the model is built to predict plausible words, not to check facts.

Retrieval-Augmented Generation fixes this by adding a lookup step. Before the model answers, the system retrieves the most relevant passages from a knowledge source you control, pastes them into the prompt, and asks the model to answer using those passages. The model still writes the sentence, but now it is reading from the right page while it does so.

Remember it asClosed-book exam (plain LLM, guessing from memory) → open-book exam (RAG, answering with the source in front of it).

Without RAG: the model guesses from stale training memory, cannot cite anything, and cannot see private data. With RAG: answers are grounded in current, specific documents, can quote sources, and update the moment you add a new file — no retraining required.

2

The librarian analogy

Imagine you ask a brilliant but forgetful friend a detailed question about a book they read years ago. Answering from memory, they get the gist right but muddle the details. Now imagine a librarian who, before your friend speaks, dashes to the shelves, pulls the three exact pages that mention your topic, and lays them open in front of your friend. Same friend, far better answer.

  1. You (the query): "What was the character's motive in chapter nine?"
  2. The librarian (the retriever): finds the passages that match your question, not by keyword alone but by meaning.
  3. The open pages (the augmented prompt): the retrieved text placed beside your question.
  4. Your friend (the generator/LLM): reads those pages and answers in natural language.
Memory hookRetriever = librarian, vector store = the shelves, chunks = the pages pulled, LLM = the friend who talks. We reuse this cast for the rest of the tutorial.

3

How it works, stage by stage

Precise definition: RAG is an architecture that conditions an LLM's output on documents fetched at inference time from an external store, using vector similarity between the query and pre-computed document embeddings.

Glossary of the moving parts

  • Embedding — a list of numbers that captures the meaning of a piece of text, so similar meanings sit close together in vector space.
  • Chunk — a document split into a bite-sized passage (often a few hundred tokens) that can be retrieved on its own.
  • Vector database — a store built to find the nearest vectors to a query vector quickly.
  • Retriever — the component that turns a query into a vector and pulls the top-k nearest chunks.
  • top-k — how many chunks you fetch (e.g. the 4 closest).
  • Context window — the maximum text the LLM can read at once; retrieved chunks must fit inside it.

4

A worked example, line by line

Say your knowledge base is a single sentence chunk: "The Q3 refund policy allows returns within 45 days." A user asks: "How long do I have to return something?"

  1. The retriever embeds the question and finds that chunk is the closest match by meaning (note it never says "45 days" in the question).
  2. The system builds a prompt: "Using this context: [refund chunk]. Answer: How long do I have to return something?"
  3. The LLM reads the chunk and answers: "You have 45 days to return an item under the Q3 refund policy."

Final result and why: the answer is correct and specific because the fact came from your document, not the model's memory. Remove the retrieval step and the model would guess a generic number.

5

Real-world: a customer-support assistant

A SaaS company points a RAG assistant at its help-centre articles, changelog, and past resolved tickets. When a customer types "my export is stuck," the retriever surfaces the three most relevant troubleshooting passages, the LLM composes a tailored reply that cites the exact article, and a human agent approves it. Because the store is re-indexed nightly, a fix shipped yesterday is answerable today — with no model retraining and no engineer in the loop.

Pro tipStore a source link with every chunk. Then the generated answer can cite it, which is what turns a chatbot people distrust into one they do.
6

Code: indexing, then answering

First you build the index once (offline). This splits documents into chunks, embeds them, and stores the vectors.

# 1. INDEXING — run once, or whenever documents change
chunks = split_into_chunks(load_documents("./docs"), size=400)
vectors = embed(chunks)                 # text -> meaning vectors
store = VectorDB()
store.add(vectors, metadata=chunks)     # keep the text + source link

What & why: chunking keeps each retrievable unit small enough to be specific and to fit the context window. Embedding happens now so that query time only needs one fast lookup, not a re-scan of every document.

Then you answer queries (online, per request):

# 2. ANSWERING — runs for every user question
def answer(question):
    q_vec = embed([question])[0]
    hits  = store.search(q_vec, top_k=4)      # nearest chunks
    context = "\n\n".join(h.text for h in hits)
    prompt = f"Use ONLY this context:\n{context}\n\nQ: {question}"
    return llm(prompt)                         # grounded answer

What & why: top_k=4 balances coverage against noise — too few misses facts, too many drowns the model. "Use ONLY this context" is the instruction that discourages the model from falling back on its own guesses.

7

RAG vs fine-tuning vs long context

ApproachBest forFreshnessCost to update
RAGFactual answers from a changing knowledge baseInstant (re-index)Low
Fine-tuningTeaching style, format, or a skillFrozen at train timeHigh (retrain)
Long context (paste it all)One-off over a small doc setPer requestHigh token cost

When to pick which: reach for RAG when facts change or are private and you need citations. Fine-tune when you need the model to behave differently, not know different facts. Use raw long context only when the whole corpus comfortably fits the window and you won't repeat the query often.

8

Best practices & common errors

Do:

  • Keep chunks semantically whole (a full paragraph or step). Why: a chunk cut mid-idea retrieves poorly.
  • Store a source link per chunk. Why: enables citations and human verification.
  • Evaluate retrieval separately from generation. Why: most bad answers are actually bad retrieval.

Common mistakes:

  • Chunks too large. Why it hurts: they blow the context budget and dilute the relevant sentence.
  • Trusting the model to say "I don't know." Why: without an instruction to refuse, it invents.
Watch outIf answers are wrong, inspect the retrieved chunks first. Nine times in ten the right passage never made it into the prompt — a retrieval bug, not a model bug.
SymptomLikely causeFix
Answer ignores your docsRetriever returned irrelevant chunksImprove chunking / embedding model; check top-k
Answer is truncatedChunks overflow the context windowLower top_k or chunk size
Model still hallucinatesNo "use only context" instructionAdd a grounding + refusal instruction
