Introduction

System, User, and Assistant messages form the conversation contract for large language models. Each role has a distinct responsibility that shapes the behavior and quality of the final answer.

  • System: Defines role/persona, tone, boundaries, and global formatting or safety rules.
  • User: States the concrete task, inputs, constraints, and success criteria.
  • Assistant: Produces the response that follows both System and User guidance.
Tip: Treat the System message as your “operating manual”, and the User message as the “work order”.

Message Structure & Syntax

Generic JSON Conversation Format
[
  {"role": "system", "content": "You are a precise technical author. Use step-by-step structure and examples."},
  {"role": "user",   "content": "Explain Python lists with syntax, examples, and a small exercise."},
  {"role": "assistant", "content": "(model will generate this response based on the above messages)"}
]
Role Purposes
RolePurposeWhat to includeWhat to avoid
System Define persona, tone, boundaries, output format. Role, audience, constraints, safety, style, formatting. Task-specific details that belong in User; ambiguous goals.
User Provide the actual task, inputs, constraints, success criteria. Goal, context, examples, data, required sections, acceptance tests. Vague asks; mixing global policies better set in System.
Assistant Produce the answer consistent with System + User. Clear structure, accurate content, follow constraints faithfully. Ignoring system rules; drifting tone; unsafe/unrequested content.

Examples

Example 1 — Educational Page Generation
[
  {"role":"system","content":"You are a helpful technical author for ItTechGenie. Use human tone, short paragraphs, and include Syntax, Example, Explanation, Notes, Practice, Summary. Output as a single HTML page only."},
  {"role":"user","content":"Topic: Python Lists. Include a TOC with anchors and two examples with outputs. Avoid hype and keep it practical."}
]
Example 2 — Tone & Safety Controls
[
  {"role":"system","content":"Act as a concise security-aware assistant. If the user requests unsafe actions, refuse and suggest safer alternatives. Keep answers under 300 words unless examples are requested."},
  {"role":"user","content":"Explain the difference between hashing and encryption with a small example."}
]
Example 3 — Output Format Guardrails
[
  {"role":"system","content":"Respond only in valid JSON. Include fields: title, summary, steps[]. Refuse non-JSON requests."},
  {"role":"user","content":"Create a 3-step checklist for enabling MFA in a web app."}
]

How the Roles Interact

  • Priority: System > User > Assistant. When in conflict, System wins.
  • Separation of Concerns: Keep persona + format in System, task + inputs in User. This improves clarity and reuse.
  • Context Chaining: Maintain a stable System across turns; refine the User message with new data or constraints.
  • Acceptance Criteria: Put measurable checks in the User message (e.g., “include 2 examples with outputs”).
Warning: Mixing style rules into the User message can cause drift. Put style and safety in the System message instead.

Real-World Use Cases

  • Documentation bots: System defines brand tone and safety; User supplies the doc request; Assistant returns a styled page.
  • Customer support: System encodes policy/compliance; User provides a ticket; Assistant returns a compliant resolution.
  • Education content: System fixes structure (sections, tone); User asks for a topic; Assistant produces consistent lessons.
  • APIs/Tools orchestration: System locks output format; User gives parameters; Assistant outputs machine-parseable results.

Key Notes / Tips

  • Write the System message once and reuse it for consistency.
  • Keep paragraphs short (2–4 lines) and avoid filler words.
  • State required sections, formats, and limits explicitly.
  • Include a tiny positive and a negative example to anchor style.
  • Log recurring mistakes, then strengthen the System message.

Practice Exercise

  1. Create a System message for your brand’s writing style, tone, and safety constraints.
  2. Write a User message requesting a page on “C# Properties” with two examples and outputs, plus a summary.
  3. Verify the output against your acceptance criteria. Iterate on the System message if there’s drift.

Summary

System messages define persona, tone, and formatting. User messages define the actual task, inputs, and success criteria. The Assistant must follow both to produce consistent, safe, and useful results. Keep roles separate and measurable for best outcomes.

Quality Checklist

  • System covers persona, tone, structure, and safety.
  • User contains a single task with clear inputs and acceptance criteria.
  • Assistant respects both and returns a single clean HTML page.
  • TOC anchors work; examples are realistic; outputs are explicit.
  • Short paragraphs; minimal CSS; readable code blocks.

FAQ

Q: Where should I put word limits?
A: In the System message if you want a global rule; in the User message if only for this task.

Q: What if the model ignores the structure?
A: Tighten the System message and restate acceptance criteria in the User message.

Q: Can I mix multiple tasks in one User message?
A: Avoid it. Split tasks for clarity and better control.
