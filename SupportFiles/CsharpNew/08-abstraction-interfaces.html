Abstraction (Hide Details, Expose Contract) #t08-abstraction-basics

Abstraction means users of your code see a simple “what” while you keep the complex “how” hidden. You expose a clear Contract so other parts of the app can depend on it safely. This reduces coupling: you can replace internals without breaking callers. In C#, abstraction is commonly achieved using abstract classes and interfaces.

Grey Example Box: “Payment” abstraction
Your checkout page shouldn’t care whether payment is via UPI, Card, or NetBanking. It should call a simple method like Pay(amount) and trust the contract. 
// Abstraction through a contract-like base type
public abstract class PaymentMethod
{
    public abstract string Name { get; }
    public abstract bool Pay(decimal amount);
}

public class UpiPayment : PaymentMethod
{
    public override string Name => "UPI";
    public override bool Pay(decimal amount)
    {
        // hidden details: UPI validation, gateway call, retries, etc.
        return amount > 0;
    }
}

// Caller depends on the abstraction, not the details:
public class CheckoutService
{
    private readonly PaymentMethod _method;
    public CheckoutService(PaymentMethod method) => _method = method;

    public bool PlaceOrder(decimal total) => _method.Pay(total);
}
Beginner Tip: When your code starts having many if/else branches for “type”, it’s a sign you need abstraction.
Advanced Note: Strong abstractions are small and stable; avoid leaking implementation details into method names or parameters.

Real-world use case: E-commerce checkout where gateways change (Paytm/PhonePe/Stripe), but checkout code stays unchanged.

ASCII Flow (Caller sees "what", implementation owns "how") [Checkout] ---> [Payment Contract] ---> [UPI Impl] | | (gateway, retries) | | | ---> [Card Impl] | ---> does NOT know internal payment steps
Warning: Over-abstracting too early can make code harder to understand. Abstract only when you have real variation.

Abstract Classes (Shared Base + Required Overrides) #t08-abstract-classes

An Abstract Class is a “partially built” base class. It can include shared fields/methods, and also force child classes to implement certain members. Choose abstract classes when you need a common base identity plus shared logic. It’s best when derived types truly share core behavior and state.

Grey Example Box: “Report Exporter” shared base
All exporters log and validate, but each exporter writes output differently (PDF vs Excel). 
public abstract class ReportExporter
{
    public void Export(string reportName, string content)
    {
        Validate(reportName, content);
        LogStart(reportName);

        WriteOutput(reportName, content); // required customization point

        LogEnd(reportName);
    }

    protected virtual void Validate(string reportName, string content)
    {
        if (string.IsNullOrWhiteSpace(reportName)) throw new ArgumentException("reportName");
        if (content is null) throw new ArgumentNullException(nameof(content));
    }

    protected abstract void WriteOutput(string reportName, string content);

    private void LogStart(string name) => Console.WriteLine($"Exporting: {name}...");
    private void LogEnd(string name)   => Console.WriteLine($"Done: {name}");
}

public class PdfExporter : ReportExporter
{
    protected override void WriteOutput(string reportName, string content)
    {
        Console.WriteLine($"[PDF] {reportName} => {content.Length} chars");
    }
}
Beginner Tip: If you need shared code + “must implement” pieces, abstract class is a natural fit.
Advanced Note: The “Template Method” style (base controls flow, derived fills steps) is powerful but keep it simple.

Real-world use case: Export pipelines (CSV/PDF/Excel) where validation/logging is identical, but output is different.

ASCII Structure (Shared base + forced customization) (abstract) ReportExporter / \ PdfExporter ExcelExporter Base controls flow: Validate -> LogStart -> WriteOutput(*) -> LogEnd
Warning: Abstract classes allow only single inheritance. If your types need many unrelated capabilities, prefer interfaces.

Abstract Methods (Must Implement) #t08-abstract-methods

An Abstract Method defines “you must implement this” for every derived class. It has no method body in the base class, so it’s purely a requirement. This guarantees important behaviors are not forgotten in derived types. Use it to enforce core actions like calculating price, validating rules, or executing a step.

Grey Example Box: Pricing rules enforced by abstract method
Every subscription plan must calculate its final monthly price, but discounts differ. 
public abstract class SubscriptionPlan
{
    public string PlanName { get; }
    protected SubscriptionPlan(string planName) => PlanName = planName;

    public decimal FinalMonthlyPrice(decimal basePrice)
    {
        if (basePrice <= 0) throw new ArgumentOutOfRangeException(nameof(basePrice));
        return CalculateFinal(basePrice); // enforced
    }

    protected abstract decimal CalculateFinal(decimal basePrice);
}

public class StudentPlan : SubscriptionPlan
{
    public StudentPlan() : base("Student") { }

    protected override decimal CalculateFinal(decimal basePrice)
        => basePrice * 0.70m; // 30% off
}

public class BusinessPlan : SubscriptionPlan
{
    public BusinessPlan() : base("Business") { }

    protected override decimal CalculateFinal(decimal basePrice)
        => basePrice + 499m; // support fee
}
Beginner Tip: If the base class cannot provide a correct default implementation, make it abstract.
Advanced Note: Prefer abstract members for “required extension points”, and keep the rest sealed/virtual only when needed.

Real-world use case: Pricing engines for different customer segments where every plan must compute final charges.

ASCII Flow (Enforced override) [FinalMonthlyPrice] | v CalculateFinal(*) --- MUST be implemented (StudentPlan / BusinessPlan / ...)
Warning: Don’t put too many abstract methods in a base class; it can become a “god base” that is hard to extend safely.

Interfaces (Pure Capability Contracts) #t08-interfaces

An Interface defines “what a type can do” without describing “how it does it.” It’s ideal for reusable capabilities like logging, caching, or repository access. Interfaces reduce coupling because callers rely on a stable contract. In real projects, you’ll see interfaces like ILogger, IRepository, or IEmailSender.

Grey Example Box: ILogger capability
Your business logic should log, but it shouldn’t care whether logs go to console, file, or cloud. 
public interface ILogger
{
    void Info(string message);
    void Error(string message);
}

public class ConsoleLogger : ILogger
{
    public void Info(string message)  => Console.WriteLine($"[INFO] {message}");
    public void Error(string message) => Console.WriteLine($"[ERROR] {message}");
}

public class OrderService
{
    private readonly ILogger _logger;
    public OrderService(ILogger logger) => _logger = logger;

    public void PlaceOrder(string orderId)
    {
        _logger.Info($"Placing order: {orderId}");
        // business logic...
        _logger.Info($"Order placed: {orderId}");
    }
}
Beginner Tip: Think of an interface like a “socket shape”: if a plug matches, it works—implementation can vary.
Advanced Note: Keep interfaces small (focused). Large interfaces create fragile dependencies and harder mocking/testing.

Real-world use case: Logging in microservices where different environments send logs to different sinks.

ASCII Capability Contract [OrderService] -- depends on --> ILogger | +------------+------------+ | | ConsoleLogger FileLogger (local dev) (production)
Warning: Don’t create interfaces for everything “just in case”. Create them when you need swapping, testing, or multiple implementations.

Multiple Inheritance via Interfaces (The C# Way) #t08-multiple-inheritance-via-interfaces

C# does not allow a class to inherit from multiple classes, but it does allow multiple interface implementations. This is the safe way to combine capabilities without complex “diamond” inheritance problems. You can build types that are loggable, cacheable, and auditable—without forcing a deep class hierarchy. This supports Composition of features.

Grey Example Box: Combine capabilities
A background job can be “trackable” and “retryable” at the same time. 
public interface ITrackable
{
    string CorrelationId { get; }
}

public interface IRetryable
{
    int MaxRetries { get; }
    bool ShouldRetry(int attempt);
}

public class DataSyncJob : ITrackable, IRetryable
{
    public string CorrelationId { get; } = Guid.NewGuid().ToString();
    public int MaxRetries => 3;

    public bool ShouldRetry(int attempt) => attempt < MaxRetries;
}
Beginner Tip: Use interfaces to “add a capability” to a type without changing its base class.
Advanced Note: Favor capability interfaces (IReadable, IWritable, ICache) over role interfaces that become too broad.

Real-world use case: Jobs and services in enterprise apps that need multiple cross-cutting behaviors (tracking, retry, auditing).

ASCII Capability Composition +-----------+ | DataSync | | Job | +-----------+ / \ implements implements ITrackable IRetryable
Warning: Too many interfaces on one class can signal “too many responsibilities”. Split the class or compose collaborators.

Interface Inheritance (Layered Capabilities) #t08-interface-inheritance

Interface inheritance lets you build a specialized contract from a more general one. This helps create layered capabilities: “basic logging” vs “structured logging”. It keeps contracts organized and makes it easy to evolve APIs without duplicating members. Use it to model “is-a-more-specific-capability” relationships.

Grey Example Box: Layered logging contract
You start with basic messages, then extend for rich context (key/value). 
public interface ILogger
{
    void Info(string message);
    void Error(string message);
}

public interface IStructuredLogger : ILogger
{
    void Info(string message, IDictionary<string, string> context);
    void Error(string message, Exception ex, IDictionary<string, string> context);
}

public class StructuredConsoleLogger : IStructuredLogger
{
    public void Info(string message) => Console.WriteLine($"[INFO] {message}");
    public void Error(string message) => Console.WriteLine($"[ERROR] {message}");

    public void Info(string message, IDictionary<string, string> context)
        => Console.WriteLine($"[INFO] {message} | ctx={context.Count}");

    public void Error(string message, Exception ex, IDictionary<string, string> context)
        => Console.WriteLine($"[ERROR] {message} | ex={ex.Message} | ctx={context.Count}");
}
Beginner Tip: Interface inheritance avoids repeating the same members in multiple interfaces.
Advanced Note: Be careful with deep interface trees; keep layering shallow and meaningful.

Real-world use case: Observability—start with simple logs, then extend to structured logs used by dashboards and alerts.

ASCII Interface Inheritance ILogger | v IStructuredLogger (adds richer operations) Implementation: StructuredConsoleLogger : IStructuredLogger
Warning: If your base interface changes often, many implementers may break. Keep base interfaces stable.

Explicit Interface Implementation (Conflict Resolution) #t08-explicit-implementation

Explicit Interface Implementation is used when: (1) two interfaces have same member names, or (2) you want to hide the interface member from the class’s public surface. The method is callable only through the interface type, not through the class variable. This helps keep your API clean and avoids confusing overloads.

Grey Example Box: Conflict resolution (same method name)
Two interfaces both define Save() but mean different things. 
public interface IUserSettings
{
    void Save();
}

public interface IDraft
{
    void Save();
}

public class ProfileEditor : IUserSettings, IDraft
{
    // Explicit implementations (not visible on ProfileEditor directly)
    void IUserSettings.Save()
    {
        Console.WriteLine("Saving user settings to DB...");
    }

    void IDraft.Save()
    {
        Console.WriteLine("Saving draft locally...");
    }

    // Public method can be a separate, clear API
    public void SaveAll()
    {
        ((IDraft)this).Save();
        ((IUserSettings)this).Save();
    }
}
Beginner Tip: If you can avoid name clashes by choosing better interface names, do that first.
Advanced Note: Explicit implementation is great for “capability hiding” so consumers see only what they need.

Real-world use case: UI editors where “Save draft” and “Save settings” are different operations but share a name.

ASCII Access Rule ProfileEditor pe = new ProfileEditor(); // pe.Save(); // NOT available IDraft d = pe; d.Save(); // OK IUserSettings s = pe; s.Save(); // OK
Warning: Overusing explicit implementation can confuse beginners. Use it when there’s a real conflict or a real need to hide.

Dynamic Polymorphism (Runtime Dispatch in Real Code) #t08-dynamic-polymorphism

Polymorphism becomes real when you store objects as an interface/base type and call methods without knowing the concrete class. The runtime dispatches the call to the correct override/implementation. This removes branching logic like “if type is X do Y”. It’s the core technique behind plug-in style designs and extensible systems.

Grey Example Box: Notification channel selection without if/else
You can add new channels later (WhatsApp, Push) without editing the sender logic. 
public interface INotifier
{
    void Send(string to, string message);
}

public class EmailNotifier : INotifier
{
    public void Send(string to, string message)
        => Console.WriteLine($"EMAIL to {to}: {message}");
}

public class SmsNotifier : INotifier
{
    public void Send(string to, string message)
        => Console.WriteLine($"SMS to {to}: {message}");
}

public class NotificationService
{
    private readonly List<INotifier> _notifiers;
    public NotificationService(List<INotifier> notifiers) => _notifiers = notifiers;

    public void Broadcast(string user, string msg)
    {
        foreach (var n in _notifiers)
            n.Send(user, msg); // runtime dispatch to EmailNotifier/SmsNotifier/...
    }
}
Beginner Tip: If you can “add a new type” without changing old code, that’s a sign polymorphism is working well.
Advanced Note: Pair polymorphism with good naming and small interfaces; otherwise you’ll move complexity from if/else into giant contracts.

Real-world use case: Notification platforms, payment gateways, report exporters, and file storage providers.

ASCII Runtime Dispatch INotifier n = new EmailNotifier(); n.Send(...) ----> EmailNotifier.Send INotifier n2 = new SmsNotifier(); n2.Send(...) ----> SmsNotifier.Send
Warning: Avoid “type checking + casting” as your default approach. It often indicates missing polymorphism.

Real-World Pattern: Dependency Injection with Interfaces #t08-di-with-interfaces

Dependency Injection means your class receives what it needs (like logger, repository) from outside. When you depend on interfaces, you can swap implementations without changing business logic. This makes unit testing easy because you can pass “fake” implementations. In modern .NET apps, DI containers automatically build objects and inject dependencies.

Grey Example Box: Repository + fake for testing
Business logic depends on IOrderRepository, not a concrete database class. 
public record Order(string Id, decimal Total);

public interface IOrderRepository
{
    Order? GetById(string id);
}

public class InMemoryOrderRepository : IOrderRepository
{
    private readonly Dictionary<string, Order> _data = new()
    {
        ["A101"] = new Order("A101", 1499m),
        ["A102"] = new Order("A102", 2999m)
    };

    public Order? GetById(string id) => _data.TryGetValue(id, out var o) ? o : null;
}

public class BillingService
{
    private readonly IOrderRepository _repo;
    private readonly ILogger _logger;

    public BillingService(IOrderRepository repo, ILogger logger)
    {
        _repo = repo;
        _logger = logger;
    }

    public decimal GetPayableAmount(string orderId)
    {
        var order = _repo.GetById(orderId);
        if (order is null)
        {
            _logger.Error($"Order not found: {orderId}");
            return 0m;
        }

        _logger.Info($"Billing for {order.Id} total={order.Total}");
        return order.Total;
    }
}
Beginner Tip: Create dependencies in the “composition root” (startup/main), not inside every class.
Advanced Note: Use small interfaces; “Fat repositories” become hard to mock and encourage business logic leakage.

Real-world use case: Switching from SQL repository to API repository during migration—business logic stays stable.

ASCII DI Flow [BillingService] -- needs --> IOrderRepository | +-- needs --> ILogger Composition Root: BillingService(repoImpl, loggerImpl)
Warning: Don’t inject too many dependencies into one class. It’s a sign the class is doing too much.

Best Practices (Prefer Composition, Keep Interfaces Small) #t08-best-practices

Strong designs use Composition more than inheritance. Keep interfaces focused so each contract describes one capability clearly. Prefer “small, stable contracts” that rarely change, because many classes will implement them. Use abstraction to protect callers from churn and keep your system maintainable as it scales.

Grey Example Box: Small interfaces + composed services
Instead of one giant service, compose small collaborators (validator + calculator + notifier). 
public interface IOrderValidator
{
    bool IsValid(string orderId);
}

public interface ITaxCalculator
{
    decimal CalculateTax(decimal amount);
}

public interface INotifier
{
    void Send(string to, string message);
}

public class OrderProcessor
{
    private readonly IOrderValidator _validator;
    private readonly ITaxCalculator _tax;
    private readonly INotifier _notifier;

    public OrderProcessor(IOrderValidator validator, ITaxCalculator tax, INotifier notifier)
    {
        _validator = validator;
        _tax = tax;
        _notifier = notifier;
    }

    public decimal Process(string orderId, decimal amount, string user)
    {
        if (!_validator.IsValid(orderId)) return 0m;

        var total = amount + _tax.CalculateTax(amount);
        _notifier.Send(user, $"Order {orderId} total payable: {total}");
        return total;
    }
}
Beginner Tip: Start with simple code, then extract an interface when you need a second implementation or testing seam.
Advanced Note: A good interface name reads like a capability: “ICache”, “IClock”, “IIdGenerator”, not “IManagerOfEverything”.

Real-world use case: Large apps where different teams swap implementations (tax rules, notifications, validation) without conflicts.

ASCII Preferred Shape Avoid: BigBaseClass -> BigDerivedClass -> BiggerDerivedClass Prefer: OrderProcessor | | | Validator Tax Notifier (small interfaces + composed collaborators)
Warning: If an interface forces implementers to throw NotImplementedException, the interface is too big.

FAQs Common doubts

1) When should I use an abstract class vs an interface?

Use an abstract class when you need shared state/behavior and a common base identity. Use an interface when you need a pure capability contract and multiple inheritance of behavior is useful.

2) Why not just use concrete classes everywhere?

Concrete-to-concrete coupling makes swapping implementations and testing harder. Contracts help keep your business logic stable even if storage/logging/payment changes.

3) Is explicit interface implementation “bad”?

No—use it when there’s a real conflict or when you intentionally want to hide a member from the public class API.

4) What is the biggest beginner mistake with interfaces?

Creating interfaces for everything “just in case”. Start simple; extract interfaces when you need multiple implementations or test seams.

Glossary (Tooltips) Term → meaning

These are the tooltip terms used in this page:

Term Tooltip Description
Abstraction A design technique where you hide internal complexity and expose only what users need.
It helps you build clean, stable APIs.
It keeps code readable and change-friendly.
Contract A promise about what an API will do (methods, inputs, outputs).
Callers rely on the contract, not internal details.
This allows implementations to change safely over time.
Abstract Class A base class that cannot be instantiated and may contain abstract members.
It can include shared code plus required overrides.
Use it when you need a common base with behavior.
Abstract Method A method declared without a body in an abstract class.
Derived classes must provide an override.
It defines a required behavior point in your design.
Interface A contract that describes capabilities without implementation details.
Classes can implement multiple interfaces to compose features.
Interfaces are great for testing and swapping implementations.
Polymorphism The ability to treat different implementations through a common base type or interface.
At runtime, the correct method implementation is chosen.
This enables extensible systems and clean architecture.
Dependency Injection A pattern where you provide dependencies from the outside instead of creating them inside.
It improves testing, reduces coupling, and supports swapping implementations.
Common in modern .NET apps with built-in DI containers.
Explicit Interface Implementation A technique where interface members are implemented so they are accessible only via the interface reference.
It helps resolve method name conflicts.
It can also hide members from the public class API.
Composition A principle where you build behavior by combining small components.
Instead of inheriting large base classes, you 'compose' capabilities.
This often improves flexibility and testability.

Hint: Use a dictionary mapping string → strategy to avoid if/else chains.

Hard 2: Pluggable Storage Provider (Interface + DI)

Problem: Create IStorage.Save(name, data) and Load(name). Implement InMemoryStorage and FileLikeStorage (simulate with a dictionary). Create DocumentService that uses IStorage and supports SaveDoc/LoadDoc.

Input/Output: Input: command sequence (SAVE/LOAD). Output: loaded content or NOT_FOUND.

Example Input/Output: Commands: SAVE a hello; LOAD a → Output: hello

Constraints: Up to 100 commands; name length ≤ 20; data length ≤ 200.

Hint: Code DocumentService only against IStorage so swapping storage changes nothing.

Hard 3: Composite Notifier (Interface Composition)

Problem: Create INotifier.Send(to,msg). Implement EmailNotifier and SmsNotifier. Create CompositeNotifier that takes a list of INotifier and sends to all. Print how many succeeded.

Input/Output: Input: message + N notifier names. Output: success count.

Example Input/Output: Input: Hi 2 Email SMS → Output: 2

Constraints: N 1..5; notifier names are unique.

Hint: CompositeNotifier just loops; each notifier returns true/false for success.

Hard 4: Rule Pipeline with Abstract Base (Template Method)

Problem: Create abstract Rule with Execute(input) that logs, validates, then calls abstract ApplyCore(input). Implement TrimRule, UppercaseRule, and ReplaceSpaceRule. Run pipeline on a string in order.

Input/Output: Input: string. Output: transformed string after all rules.

Example Input/Output: Input: " hi gopi " → Output: HI_GOPI

Constraints: Input length ≤ 500.

Hint: Base Execute() controls steps; derived only changes ApplyCore().

Hard 5: Conflict Interfaces + Hidden API (Explicit Implementation)

Problem: Create IReadable.Read() and IResettable.Read() with same signature but different meaning (one reads data, one reads reset status). Implement both explicitly in Device. Based on input mode, call the correct Read and print result.

Input/Output: Input: mode (data/reset). Output: returned string.

Example Input/Output: Input: reset → Output: RESET_OK

Constraints: Must not expose public Read() on Device.

Hint: Use explicit implementations and cast Device to the requested interface before calling Read().
