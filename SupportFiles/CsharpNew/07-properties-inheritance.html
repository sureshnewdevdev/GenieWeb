Why Properties? (Encapsulation Without Boilerplate)

Subtopic 1 / 10

A property is a clean way to expose state while still protecting your object’s rules. Instead of public fields (which allow “anything”), properties let you control read/write access using Method-like logic. This is the practical face of Encapsulation. Your class becomes safer, easier to maintain, and easier to evolve without breaking callers.

+-------------------+ set value +----------------------+ | Outside World | ------------------> | Property (setter) | | (other classes) | | validates / guards | +-------------------+ +----------+-----------+ | v +------+------+ | Private | | Field | +------+------+ ^ | +-------------------+ get value +-------+------+ | Outside World | <------------------ | Property (get)| +-------------------+ +--------------+

Example (Bad vs Good)

Bad: public field allows invalid state anytime.
public class BankAccount
{
    public decimal Balance; // anyone can set: -999999
}
Good: property controls updates and protects rules.
public class BankAccount
{
    private decimal _balance;

    public decimal Balance
    {
        get { return _balance; }
        private set { _balance = value; } // restrict external write
    }

    public void Deposit(decimal amount)
    {
        if (amount <= 0) throw new ArgumentException("Amount must be positive.");
        Balance = Balance + amount;
    }
}

Real-world use case: In a payroll system, you never want someone to directly set salary/bonus fields from random screens. Properties let you restrict writes and keep logic in one place.

Beginner tip: Prefer properties over public fields for almost every class you expose to other code.
Advanced note: Properties help you keep invariants (rules that must always be true). When the rule changes, you update it in one place instead of chasing field writes across the project.

Auto-Implemented Properties (Fast and Clean)

Subtopic 2 / 10

Auto-properties are the quickest way to create properties when you don’t need custom logic. The compiler creates a hidden “backing field” for you, so your class stays short and readable. This is perfect for DTOs, simple models, and UI binding scenarios. You still get the benefits of properties (future flexibility) without boilerplate.

You write: Compiler generates: --------- ------------------- public string Name { private string k__BackingField; get; set; } public string Name { get => k__BackingField; set => k__BackingField = value; }

Example (Simple Student Model)

public class Student
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public string Email { get; set; } = "";
    public int Grade { get; set; }
}

// Usage
var s = new Student { Id = 101, Name = "Aarav", Email = "aarav@mail.com", Grade = 9 };
Console.WriteLine($"{s.Id} - {s.Name} - Grade {s.Grade}");

Real-world use case: In Web API responses, you often return clean “data shapes” (DTOs). Auto-properties keep these classes tiny and consistent.

Beginner tip: Use auto-properties by default. Switch to a full property only when you truly need validation or side-effects.
Advanced note: You can combine auto-properties with restricted setters like private set to make objects “readable from outside, writable only inside.”

Full Properties with Validation (get/set Logic)

Subtopic 3 / 10

Full properties are used when you must enforce rules while setting a value. Here, you explicitly store data in a private field and write logic inside the setter. This prevents invalid data from ever entering the object, which avoids bugs later. Typical examples include age, price, stock quantity, and dates.

SET Age(value) | v Is value < 0 ? / \ Yes No / \ throw _age = value error | v object stays valid

Example (Age Validation)

public class UserProfile
{
    private int _age;

    public int Age
    {
        get { return _age; }
        set
        {
            if (value < 0) throw new ArgumentException("Age cannot be negative.");
            if (value > 130) throw new ArgumentException("Age seems unrealistic.");
            _age = value;
        }
    }

    public string Name { get; set; } = "";
}

// Demo
var u = new UserProfile { Name = "Meera" };
u.Age = 25;             // OK
// u.Age = -2;          // throws exception

Real-world use case: In e-commerce, you must stop “negative stock” at the model level, not only in the UI. Validation in properties protects data even when updates come from APIs or background jobs.

Beginner tip: Keep validations short and clear. If logic becomes large, move it to a method (e.g., ChangeAge(value)) and call it from the setter.
Advanced note: Choose between exceptions vs “Try-set” patterns depending on context. For user input, you might prefer validation messages rather than throwing and crashing flows.

Read-Only / Write-Only Patterns (When to Restrict Access)

Subtopic 4 / 10

Sometimes a value should be visible but not editable (read-only), or updateable but not directly readable (rare). Read-only patterns prevent accidental changes and make your objects more reliable. In C#, you commonly restrict setters using private set or provide only a getter that returns a calculated value. This also supports safer APIs in layered applications (UI → service → domain).

Read-only from outside: Outside code: obj.Id = 10; ❌ blocked Console.Write(obj.Id); ✅ allowed Inside class: Id can be set in constructor or methods ✅

Example (Order Id read-only + Password write-only-like)

public class Order
{
    public int Id { get; private set; }      // readable everywhere, writable only inside
    public DateTime CreatedAt { get; }       // getter-only property (set in constructor)

    private string _passwordHash = "";

    public Order(int id)
    {
        Id = id;
        CreatedAt = DateTime.UtcNow;
    }

    // "Write-only-like" pattern via method (recommended)
    public void SetPassword(string rawPassword)
    {
        if (string.IsNullOrWhiteSpace(rawPassword) || rawPassword.Length < 8)
            throw new ArgumentException("Password must be at least 8 characters.");

        _passwordHash = "HASHED:" + rawPassword; // demo only
    }
}

Real-world use case: In banking, account numbers and created timestamps should never change after creation. Read-only properties stop accidental “data corruption” across multiple screens and services.

Beginner tip: If a property should never change after creation, use a getter-only property and set it in the constructor.
Advanced note: For sensitive data (like passwords), avoid storing raw values and avoid public getters. Use methods that store only hashed/derived values.

Indexers (Object Access Like an Array)

Subtopic 5 / 10

An indexer lets your object be accessed using bracket syntax like an array. Internally, you usually wrap a collection (like a list or dictionary) but expose controlled access. This makes your API feel natural: callers can do obj[key] instead of calling methods everywhere. Indexers are great when your class represents a “container-like” object.

+---------------------+ | StudentDirectory | | (wraps Dictionary) | +----------+----------+ | directory["Aarav"] ---> returns Student object | uses internal dictionary lookup

Example (Directory with Indexer)

public class Student
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
}

public class StudentDirectory
{
    private readonly Dictionary<string, Student> _byName = new();

    public Student this[string name]
    {
        get
        {
            if (!_byName.ContainsKey(name))
                throw new KeyNotFoundException("Student not found: " + name);
            return _byName[name];
        }
        set
        {
            if (string.IsNullOrWhiteSpace(name))
                throw new ArgumentException("Name key cannot be empty.");
            _byName[name] = value;
        }
    }
}

// Demo
var dir = new StudentDirectory();
dir["Aarav"] = new Student { Id = 1, Name = "Aarav" };
Console.WriteLine(dir["Aarav"].Id);

Real-world use case: A configuration object can expose settings via keys: config["ConnectionString"], but still validate and provide defaults internally.

Beginner tip: Start with a dictionary-based indexer. Add validation and good error messages so callers understand what went wrong.
Advanced note: Indexers can be read-only by omitting the setter, which is useful when you want safe access but no direct mutation.

Indexer Overloading (Multiple Key Types)

Subtopic 6 / 10

Indexers can be overloaded to support different key types (like int and string). This is useful when users naturally search by ID sometimes and by name at other times. The idea is similar to Overloading methods: same “concept”, different inputs. Done well, it creates a friendly API; done poorly, it can confuse callers.

Directory access choices: dir[5] -> find by Id (int key) dir["Meera"] -> find by Name (string key) Same object, two indexer signatures

Example (Access by Id and Name)

public class Employee
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
}

public class EmployeeDirectory
{
    private readonly Dictionary<int, Employee> _byId = new();
    private readonly Dictionary<string, Employee> _byName = new(StringComparer.OrdinalIgnoreCase);

    public Employee this[int id]
    {
        get { return _byId[id]; }
        set
        {
            _byId[id] = value;
            _byName[value.Name] = value;
        }
    }

    public Employee this[string name]
    {
        get { return _byName[name]; }
        set
        {
            _byName[name] = value;
            _byId[value.Id] = value;
        }
    }
}

// Demo
var d = new EmployeeDirectory();
d[101] = new Employee { Id = 101, Name = "Rahul" };
Console.WriteLine(d["Rahul"].Id);
Console.WriteLine(d[101].Name);

Real-world use case: In a helpdesk app, an agent may search tickets by ticket number (int) or customer email/name (string). Overloaded indexers make both fast and natural.

Beginner tip: Keep the behavior consistent across overloads (same rules, same error style), otherwise debugging becomes hard.
Advanced note: Consider what happens when keys change (e.g., name updates). You may need methods that handle re-indexing safely instead of naive assignments.

Inheritance Basics (is-a Relationship)

Subtopic 7 / 10

Inheritance means one class derives from another to reuse and extend behavior. It models an “is-a” relationship (Manager is an Employee). You put shared fields/methods in the base class, and specialized parts in the derived class. This reduces duplication and supports Polymorphism.

Employee (base) +--------------------+ | Id, Name | | CalculatePay() | +---------^----------+ | | +---------+----------+ | Manager (derived) | | TeamSize | | CalculatePay() | +-------------------+

Example (Employee → Manager)

public class Employee
{
    public int Id { get; set; }
    public string Name { get; set; } = "";

    public virtual decimal CalculatePay()
    {
        return 30000m; // base salary
    }
}

public class Manager : Employee
{
    public int TeamSize { get; set; }

    public override decimal CalculatePay()
    {
        // Managers get base + responsibility allowance
        return 30000m + (TeamSize * 500m);
    }
}

// Demo (polymorphism)
Employee e1 = new Employee { Id = 1, Name = "Sita" };
Employee e2 = new Manager { Id = 2, Name = "Arjun", TeamSize = 6 };

Console.WriteLine(e1.CalculatePay()); // 30000
Console.WriteLine(e2.CalculatePay()); // 33000

Real-world use case: In HR systems, different employee types (FullTime, Contract, Intern) share identity details but calculate pay differently. Inheritance helps unify shared data and vary only what changes.

Beginner tip: Use inheritance only when it truly is an “is-a” relationship. If it’s more like “has-a” (car has an engine), prefer composition.
Advanced note: Keep base classes small and stable. Too much in a base class creates rigid designs and makes future changes risky.

base Keyword (Constructor + Member Access)

Subtopic 8 / 10

The base keyword helps a derived class call the base class constructor and access base members. This matters when the base class requires initialization parameters or has logic you must reuse. Without proper base calls, your object may start in an incomplete state. Think of base as “first build the shared part, then add the specialized part.”

new Manager(id,name,teamSize) | v Manager ctor starts | v calls base(id,name) | v Employee ctor sets Id/Name | v returns to Manager ctor | v Manager sets TeamSize

Example (Base Constructor Call)

public class Employee
{
    public int Id { get; }
    public string Name { get; }

    public Employee(int id, string name)
    {
        Id = id;
        Name = name;
    }

    public virtual string GetBadgeText()
    {
        return $"EMP-{Id}: {Name}";
    }
}

public class Manager : Employee
{
    public int TeamSize { get; }

    public Manager(int id, string name, int teamSize)
        : base(id, name) // call base constructor
    {
        TeamSize = teamSize;
    }

    public override string GetBadgeText()
    {
        return base.GetBadgeText() + $" (Manager, Team={TeamSize})";
    }
}

// Demo
var m = new Manager(12, "Nisha", 8);
Console.WriteLine(m.GetBadgeText());

Real-world use case: In a company ID-card system, base class can format the badge consistently, and derived classes add extra label info (Admin, Manager, Contractor) using base behavior.

Beginner tip: If your base class has no parameterless constructor, you must call a base constructor explicitly.
Advanced note: Use base calls to reuse tested behavior (like formatting, common validation). This prevents duplicated logic across derived types.

Overriding vs Hiding (virtual/override vs new)

Subtopic 9 / 10

Overriding is true runtime polymorphism: base references call the derived behavior when a method is marked virtual and implemented with override. Hiding using new creates a separate method that depends on the variable’s compile-time type, which can surprise you. Learn this difference early to avoid confusing bugs in inheritance hierarchies.

Overriding (runtime): BaseRef -> calls Derived override ✅ Hiding (compile-time): BaseRef -> calls Base method DerivedRef -> calls Derived method (same object, different call result)

Example (Override vs new)

public class Report
{
    public virtual string Generate()
    {
        return "Base Report";
    }
}

public class SalesReport : Report
{
    public override string Generate()
    {
        return "Sales Report (override)";
    }
}

public class AuditReport : Report
{
    // Hides, does NOT override
    public new string Generate()
    {
        return "Audit Report (new)";
    }
}

// Demo
Report r1 = new SalesReport();
Console.WriteLine(r1.Generate()); // Sales Report (override)

Report r2 = new AuditReport();
Console.WriteLine(r2.Generate()); // Base Report  (because hiding)

AuditReport r3 = new AuditReport();
Console.WriteLine(r3.Generate()); // Audit Report (new)

Real-world use case: In a notification system (Email, SMS, Push), you want base references to call the correct derived send logic. That requires overriding; hiding would cause wrong channel behavior.

Beginner tip: If your goal is “base variable should call derived behavior,” always use virtual/override.
Advanced note: Use new only when you intentionally want to change the public surface for a derived type (rare). Prefer clearer designs or composition if you often feel the need to hide members.

Sealed Classes & Methods (Locking Down Behavior)

Subtopic 10 / 10

The sealed keyword prevents further inheritance (for classes) or prevents further overriding (for methods). This is useful when a type’s behavior must not change (security rules, domain invariants, or performance-sensitive code). Sealing reduces unexpected modifications and can make code easier to reason about. Use it thoughtfully—too much sealing can make systems hard to extend.

sealed class PaymentProcessor | +--> cannot derive: class CustomProcessor : PaymentProcessor ❌ compile error override method can be sealed too: Base virtual -> Derived override sealed -> no further overrides

Example (Sealed Class + Sealed Override)

public sealed class PaymentToken
{
    public string Value { get; }
    public PaymentToken(string value) => Value = value;
}

public class Logger
{
    public virtual string Format(string message) => "[LOG] " + message;
}

public class SecureLogger : Logger
{
    public sealed override string Format(string message)
    {
        // enforce security prefix (demo)
        return "[SECURE] " + message;
    }
}

// This would fail:
// public class CustomLogger : SecureLogger { public override string Format(string m) => m; }

Real-world use case: In authentication/authorization modules, you may seal key types so nobody can override them and bypass security behavior.

Beginner tip: Use sealed when you are confident the type should not be extended (utility types, tokens, stable domain objects).
Advanced note: Sealing can improve maintainability and sometimes performance, but it trades away extensibility—balance these based on your project needs.

FAQs

Quick clarity

1) Are properties “just fields”?

No. Properties are access points that can run logic on get/set. They can protect rules and control access, unlike public fields.

2) When should I switch from auto-property to full property?

When you need validation, logging, lazy loading, computed values, or restricted access beyond a simple set.

3) Is a write-only property recommended?

It’s rare and often confusing. Prefer a method (like SetPassword) for write-only-like behavior.

4) Indexer vs method: which is better?

Indexer is great when your object acts like a collection. Methods are clearer when many rules or actions happen during access.

5) Does inheritance always mean better reuse?

Not always. If it’s not an “is-a” relationship, inheritance can create rigid designs. Use composition for “has-a”.

6) What is the biggest risk with method hiding using new?

Calls depend on variable type. A base reference may call base behavior even when the object is derived—this surprises many developers.

7) When should I use sealed?

When extension would break correctness/security, or when a type must stay stable (tokens, core domain invariants, security components).

8) Can I override a non-virtual method?

No. The base method must be virtual (or abstract) to be overridden in derived classes.

Interview Questions (with short answers)

Job-ready review

1) Why do properties exist in C#?

To expose data safely with controlled access (validation, restricted setters) while keeping a simple field-like syntax for callers.

2) Auto-property vs full property: explain the difference.

Auto-property uses a compiler-generated backing field; full property uses an explicit private field and custom get/set logic.

3) What is a backing field and why do we use it?

It stores the actual value behind a property. We use it when we need custom rules or additional logic during get/set.

4) Explain private set. Where is it useful?

It allows external read but restricts write to inside the class. Useful for Ids, timestamps, and domain state changes through methods only.

5) What is an indexer and when would you use it?

An indexer enables obj[key] access. Use it when your type wraps a collection and you want natural, controlled access.

6) Can you overload indexers? Give a real case.

Yes, by changing parameter types. Example: ticket directory access by ticketId (int) and customerEmail (string).

7) What is the difference between overriding and hiding?

Overriding (virtual/override) dispatches at runtime based on actual object type; hiding (new) depends on reference variable type.

8) Why should you be careful with base classes?

Too much logic in base classes creates tight coupling. Changes can break many derived classes, and the design becomes rigid.

9) What does the base keyword do?

It accesses base members and invokes base constructors to initialize shared state or reuse base behavior.

10) When is sealed appropriate?

When you must prevent extension/override for correctness or security (e.g., authentication tokens, secure log formatting).

11) How do properties help maintain invariants?

Setters can enforce rules so invalid values never enter the object—this protects correctness across the entire codebase.

12) Give a quick example where composition is better than inheritance.

A Car has an Engine. Engine is not a type of Car; it’s a part of Car. Use composition to model this “has-a” relationship.

Summary

Key takeaways
  • Use properties to keep state safe and future-proof your API (avoid public fields).
  • Auto-properties are best for simple models; full properties are best when you need validation or side-effects.
  • Restrict mutability with private setters or getter-only properties to protect important values.
  • Indexers make container-like classes feel natural while still enforcing rules.
  • Inheritance should model “is-a”; for “has-a”, prefer composition.
  • Overriding enables true polymorphism; hiding using new can surprise you.
  • Use base to reuse initialization/behavior; use sealed to lock down critical behavior.
Beginner reminder: Start simple (auto-properties), then add rules only when needed.
Advanced reminder: Design for change: stable base types, clear invariants, and minimal surprises in polymorphism.

Glossary (Tooltips)

Terms used in this module

These are the tooltip meanings used across this page.

Term Tooltip Description
Encapsulation Keeping an object’s internal state protected and exposing safe ways to interact with it. You typically use private fields and public methods/properties to enforce rules.
Indexers Allows objects to be accessed using array-like syntax (obj[key]). Indexers are commonly used to wrap internal collections with controlled access.
Inheritance A relationship where a class derives from another class to reuse and extend behavior. It models an 'is-a' relationship and enables polymorphism.
Polymorphism The ability to treat different derived types through a common base type or interface. Calls resolve to the correct implementation at runtime using overriding.
virtual Marks a method as overridable in derived classes. It enables runtime polymorphism by allowing derived classes to replace the base behavior.
override Replaces a base class virtual/abstract method with a derived implementation. The runtime calls the most derived override when accessed via the base type.
sealed Prevents further inheritance or overriding. Use sealed to lock down behavior for security, correctness, or performance reasons.
base Used in derived classes to access base members and to call base constructors. It helps initialize shared state and reuse base behavior safely.
Overloading Having multiple methods with the same name but different parameter lists. It improves API usability but should be used carefully to avoid confusion.
Method A named block of code that performs an action. Methods can accept inputs and return outputs. They help reuse and organize logic.

Input/Output: Input: new Teacher(5,"Anita","Math"). Output: print formatted info.
Example Input: (5,"Anita","Math")
Example Output: 5 - Anita - Math
Constraints: Subject cannot be empty.
Hint: Use : base(id,name) in derived constructor.

Hard (5)

H1) Prevent Invalid State with Sealed Override

Problem: Build Logger → SecureLogger where SecureLogger overrides Format() and seals it to enforce a prefix. Demonstrate that further override is not allowed.
Input/Output: Input: message string. Output: formatted message.
Example Input: "Payment Approved"
Example Output: "[SECURE] Payment Approved"
Constraints: Must compile without exposing a way to remove the prefix.
Hint: Use sealed override in derived class.

H2) Override vs new Bug Demonstration

Problem: Create base Notifier.GenerateMessage(). Create EmailNotifier that overrides, and SmsNotifier that hides with new. Show different outputs when referenced as base type.
Input/Output: Input: create objects and call method. Output: printed messages showing mismatch.
Example Input: Notifier n = new SmsNotifier(); n.GenerateMessage()
Example Output: Base message (unexpected) + explain why
Constraints: Include comments in code explaining the behavior.
Hint: Use virtual/override for correct polymorphism; use new for hiding.

H3) Indexer with Range Support

Problem: Create a GradeBook that stores marks and provides: this[int index] to read/write and a method GetRange(int start,int end) returning a formatted string summary.
Input/Output: Input: marks list + range. Output: "avg, min, max" for that range.
Example Input: marks: 70,80,90,60,50; range 1..3
Example Output: avg=76.67 min=60 max=90
Constraints: Validate start/end and ensure start <= end.
Hint: Wrap a List<int> and compute safely.

H4) Immutable Domain Object Pattern

Problem: Build a Money class with Amount and Currency that cannot be changed after creation. Provide Add(Money other) that returns a NEW Money.
Input/Output: Input: money1 + money2. Output: new Money and original unchanged.
Example Input: (100,"INR") + (50,"INR")
Example Output: (150,"INR")
Constraints: Currency must match; otherwise error.
Hint: Use getter-only properties and return new instance.

H5) Polymorphic Billing Engine

Problem: Create base Plan class with virtual CalculateBill(usage). Derived plans: BasicPlan, ProPlan, EnterprisePlan with different rates and caps. Use a List<Plan> to calculate bills for different customers.
Input/Output: Input: plan + usage. Output: bill amount for each customer.
Example Input: Basic usage=120; Pro usage=120
Example Output: Different bills based on plan rules
Constraints: Usage must be non-negative; Enterprise may have discount beyond threshold.
Hint: Put shared logic in base, vary only rate rules in overrides.
