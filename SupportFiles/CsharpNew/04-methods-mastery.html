1) Method Anatomy (Signature, Return Type, Parameters)

Write methods correctly + know what “signature” means

A Method is defined by its name, return type, and its parameter list.
The method signature is mainly the method name + parameter types/order (return type is not part of signature for overload resolution).
A good return type tells the caller what they get back, and avoids “mystery outputs”.
Keep parameters minimal and meaningful to make the API easy to test and reuse.
If a method does one job clearly, your code becomes readable and maintainable. 

Flow: Caller -> Method Call -> Execute Body -> Return Value
        ┌────────┐   args   ┌─────────────────┐   result   ┌────────┐
        │ Caller │ ───────> │   Method Body   │ ────────> │ Caller │
        └────────┘          └─────────────────┘            └────────┘
Example (Grey Box): Identify parts of a method
Name: CalculateTotal
Return Type: decimal
Parameters: price, quantity
Body: multiply and return 
using System;

public class Billing
{
    // Return type: decimal
    // Method name: CalculateTotal
    // Parameters: (decimal price, int quantity)
    public static decimal CalculateTotal(decimal price, int quantity)
    {
        decimal total = price * quantity;
        return total;
    }

    public static void Main()
    {
        decimal bill = CalculateTotal(199.50m, 3);
        Console.WriteLine($"Total = {bill}");
    }
}

Real-world use case

In an e-commerce checkout, a method like CalculateTotal keeps billing logic in one place so UI, API, and tests all reuse the same calculation.

Design hint

Prefer returning a value instead of printing inside the method—this keeps the method reusable and makes unit testing simpler.

Beginner Tip

Pick method names as verbs (Calculate, Validate, Convert). It reads like a sentence.

Advanced Note

Design methods to be “pure” when possible: same inputs → same output, no hidden side effects.

2) Static Methods vs Instance Methods (How to Call Them)

Choose static/instance based on responsibility and state

A static method belongs to the class, so you call it using the type name.
An instance method belongs to an object, so you call it on a created object (instance).
Use static when behavior does not depend on object state (pure utility / helper behavior).
Use instance methods when the method uses or changes an object’s internal data.
This decision affects testability, design clarity, and how state is managed. 

Decision guide:
  Does it need object state?
    Yes -> Instance method (obj.DoWork())
    No  -> Static method   (Type.DoWork())
Example (Grey Box): When to use what
Static: Math helpers, parsing helpers, formatting helpers
Instance: BankAccount.Deposit(), Cart.AddItem(), User.ChangePassword() 
using System;

public class TemperatureConverter
{
    // Static: conversion does not need instance state
    public static double CelsiusToFahrenheit(double c) => (c * 9 / 5) + 32;
}

public class BankAccount
{
    private decimal _balance; // object state

    public BankAccount(decimal opening) { _balance = opening; }

    // Instance: depends on and changes state
    public void Deposit(decimal amount) => _balance += amount;

    public decimal GetBalance() => _balance;
}

public class Demo
{
    public static void Main()
    {
        // Call static
        Console.WriteLine(TemperatureConverter.CelsiusToFahrenheit(30));

        // Call instance
        var acc = new BankAccount(1000m);
        acc.Deposit(250m);
        Console.WriteLine(acc.GetBalance());
    }
}

Real-world use case

In a fintech app, BankAccount methods must be instance methods because each account has its own balance state.

Common mistake

Putting everything static makes code hard to evolve (global-like behavior). Prefer instance methods for domain objects.

Beginner Tip

If you see “new” before calling, you’re using an instance method.

Advanced Note

Static can be fine for stateless helpers, but consider dependency injection for testable services.

3) Parameters & Return Values (Designing Clean APIs)

Pass inputs and return outputs in a clean, testable way

A Parameter is the input a method needs to perform its job.
A return value is the output that should be used by the caller (not printed inside the method).
Prefer returning results and letting the caller decide what to do (display, store, send to API).
Keep parameter lists small; too many parameters usually means your method has too many responsibilities.
If you need multiple outputs, consider returning a tuple or a small result object (or use out in specific patterns). 

Clean API pattern:
  Input parameters -> Work -> Return result
  (No hidden reads/writes if avoidable)
Example (Grey Box): “Validate + Return errors”
A validation method can return a boolean (valid/invalid) and a message to explain the failure. 
using System;

public static class UserRegistration
{
    // Returns a bool and also returns a message (classic pattern)
    public static bool TryValidateEmail(string email, out string message)
    {
        if (string.IsNullOrWhiteSpace(email))
        {
            message = "Email is required.";
            return false;
        }

        if (!email.Contains("@"))
        {
            message = "Email must contain @.";
            return false;
        }

        message = "OK";
        return true;
    }

    public static void Main()
    {
        bool ok = TryValidateEmail("gopi.example.com", out string msg);
        Console.WriteLine($"Valid? {ok} | Message: {msg}");
    }
}

Real-world use case

In a registration API, validation methods return results instead of writing to console, so the same logic works for web, mobile, and automated tests.

API cleanliness rule

If a method name starts with “Try…”, it should not throw for normal invalid input; it should return success/failure.

Beginner Tip

Return values are more reusable than printing. Printing is “UI logic”, not “business logic”.

Advanced Note

Prefer small dedicated parameter objects when you have many related inputs (improves readability and versioning).

4) Method Overloading (Same Name, Different Parameters)

Build flexible methods without confusing names

Overloading means same method name, but different parameter types or counts.
The compiler chooses the best match based on the call’s arguments.
Overloads help create friendly APIs (one concept, multiple input styles).
Avoid overloads that are too similar (can cause ambiguous calls and confusion).
Prefer overloads that clearly represent different “ways to provide the same data”. 

Overload resolution idea:
  Print(5)      -> chooses Print(int)
  Print("Hi")   -> chooses Print(string)
  Print(5, "A") -> chooses Print(int, string)
Example (Grey Box): Same intent, different inputs
A logging helper can accept a message, or a message + severity, without forcing different names. 
using System;

public static class AppLogger
{
    public static void Log(string message)
    {
        Console.WriteLine($"INFO: {message}");
    }

    public static void Log(string message, string severity)
    {
        Console.WriteLine($"{severity.ToUpper()}: {message}");
    }

    public static void Log(Exception ex)
    {
        Console.WriteLine($"ERROR: {ex.Message}");
    }

    public static void Main()
    {
        Log("Service started");
        Log("Disk space low", "warning");
        Log(new InvalidOperationException("Invalid state"));
    }
}

Real-world use case

In production apps, logging methods often have overloads so developers can log quickly without repeating common parameters everywhere.

Safety tip

If you notice developers calling the wrong overload often, your overload set is probably too confusing.

Beginner Tip

Overloads differ by parameters, not by return type.

Advanced Note

Be careful with overloads involving null and optional parameters—calls can become ambiguous.

5) Optional, Named Arguments (Readable Calls)

Improve readability and reduce repetitive overloads

Optional parameters let callers omit values when a sensible default exists.
Named arguments let callers specify parameter names, making calls readable and reducing mistakes.
Use optional parameters for stable defaults (like retryCount = 3).
Use named arguments when a method has multiple similar parameters (like startDay, endDay).
Keep optional parameters at the end of the parameter list for clarity. 

Readable call styles:
  SendEmail("a@x.com", "Hi", isHtml: true)
  BookRoom(roomId: 12, nights: 3, includeBreakfast: true)
Example (Grey Box): Notification sender
Default retries and timeout, but allow overrides only when needed. 
using System;

public static class Notifier
{
    public static void Send(string to, string message, int retryCount = 3, int timeoutSeconds = 10)
    {
        Console.WriteLine($"To={to} | Msg={message} | Retries={retryCount} | Timeout={timeoutSeconds}s");
    }

    public static void Main()
    {
        // Uses defaults
        Send("ops@company.com", "Service healthy");

        // Named args for clarity
        Send(to: "ops@company.com", message: "Service slow", timeoutSeconds: 30, retryCount: 5);
    }
}

Real-world use case

In alerting systems, defaults handle 90% of cases, while named arguments make the “special case” configuration obvious and self-documenting.

Readable API rule

If a call looks confusing, named arguments usually make it instantly understandable.

Beginner Tip

Named arguments reduce “what does this number mean?” confusion in method calls.

Advanced Note

Changing optional parameter defaults can be risky in shared libraries—callers compiled earlier may still use old defaults.

6) params (Variable Number of Arguments)

Accept flexible argument counts safely

The params keyword lets callers pass many values without manually creating an array.
Inside the method, you receive the values as an array, so you can loop safely.
Use this for convenience APIs like Sum, Log, or AddMany, where variable counts are natural.
Avoid params when the method already has many parameters; it can reduce readability.
Prefer strong input validation, because callers might pass nothing (empty array). 

params behavior:
  Sum(1,2,3)  -> numbers = [1,2,3]
  Sum()       -> numbers = []
Example (Grey Box): Cart total from many item prices
A cart might accept multiple item prices and compute the total quickly. 
using System;

public static class Pricing
{
    public static decimal SumPrices(params decimal[] prices)
    {
        decimal total = 0m;
        foreach (var p in prices)
            total += p;
        return total;
    }

    public static void Main()
    {
        Console.WriteLine(SumPrices(99.99m, 199.50m, 49.00m));
        Console.WriteLine(SumPrices()); // empty list -> 0
    }
}

Real-world use case

In reporting utilities, you can accept a flexible set of values (daily sales) and compute totals/averages without forcing callers to allocate arrays manually.

Practical caution

params may allocate an array under the hood; it’s fine for most apps, but measure in hot loops.

Beginner Tip

If you can call a method with “comma separated values”, params is probably being used.

Advanced Note

For performance-critical paths, consider overloads that accept ReadOnlySpan to avoid allocations (advanced topic).

7) ref / out / in (By-Reference Parameter Patterns)

Use reference semantics when performance or multi-returns matter

ref passes a variable by reference, so changes inside the method affect the caller.
out is used for additional outputs; the method must assign it before returning.
in passes by reference but read-only, useful for large value types where copying is expensive.
Use these carefully: they are powerful but can reduce readability if overused.
If your method returns many values, consider returning a small object/record (cleaner API). 

By-reference idea:
  Caller variable  <---- shared ---->  Method parameter
  Changes can flow back (ref/out), or be read-only (in)
Example (Grey Box): TryParse pattern
Return true/false, and output the parsed result only on success. 
using System;

public static class Input
{
    public static bool TryReadPositiveInt(string text, out int value)
    {
        bool ok = int.TryParse(text, out value);
        if (!ok) return false;
        if (value <= 0) { value = 0; return false; }
        return true;
    }

    public static void ApplyDiscount(ref decimal price, decimal percent)
    {
        price = price - (price * percent / 100m);
    }

    public static decimal Perimeter(in (decimal W, decimal H) rect)
    {
        // rect is read-only inside method
        return 2m * (rect.W + rect.H);
    }

    public static void Main()
    {
        if (TryReadPositiveInt("25", out int qty))
            Console.WriteLine($"Qty = {qty}");

        decimal p = 1000m;
        ApplyDiscount(ref p, 10m);
        Console.WriteLine($"Discounted price = {p}");

        var r = (W: 10m, H: 5m);
        Console.WriteLine($"Perimeter = {Perimeter(in r)}");
    }
}

Real-world use case

Payment validation often uses Try-pattern methods (return success + out result), so the API stays safe and avoids exceptions for normal invalid input.

When not to use

If your team frequently misunderstands data flow, prefer returning a result object instead of ref/out.

Beginner Tip

Use out when you want “extra output”, and ref when you want to “modify an existing variable”.

Advanced Note

in can help performance for large structs, but always measure—clarity beats micro-optimizations.

8) Local Functions & Static Local Functions

Organize helper logic without polluting the class API

Local functions are methods declared inside another method to support that method’s logic.
They keep helper code close to where it is used, improving readability and reducing “helper clutter”.
A static local function cannot capture outer variables, which can improve safety and clarity.
Use local functions when the logic is not useful anywhere else outside that parent method.
This is especially useful for validation, parsing steps, and small repeated calculations. 

Local function structure:
  ParentMethod()
    ├─ Step A
    ├─ Helper()   (local function)
    └─ Step B
Example (Grey Box): Invoice calculation with a local helper
You can keep rounding/formatting logic local to the invoice method to avoid extra public methods. 
using System;

public static class Invoice
{
    public static decimal CalculateFinal(decimal price, int qty, decimal taxPercent)
    {
        decimal subtotal = price * qty;
        decimal tax = CalcTax(subtotal, taxPercent);
        return Round2(subtotal + tax);

        decimal CalcTax(decimal amount, decimal percent)
        {
            return amount * percent / 100m;
        }

        static decimal Round2(decimal amount)
        {
            return Math.Round(amount, 2, MidpointRounding.AwayFromZero);
        }
    }

    public static void Main()
    {
        Console.WriteLine(CalculateFinal(199.99m, 2, 18m));
    }
}

Real-world use case

In billing services, local functions let you keep “small steps” (tax, discounts, rounding) together so the invoice method reads like a clear recipe.

Clean code benefit

Fewer public helper methods means a smaller public API surface and less accidental misuse.

Beginner Tip

Use local functions when you feel “this helper is only for this one method”.

Advanced Note

Static local functions reduce accidental capture of outer variables, which can prevent subtle bugs.

9) Recursion Basics (Base Case + Recursive Case)

Understand recursion correctly without fear

Recursion is when a method solves a problem by calling itself on a smaller version of the same problem.
Every recursive solution needs a base case (stop condition) and a recursive case (the self-call).
If the base case is missing or unreachable, you can get a stack overflow (too many calls).
Think of recursion like “keep reducing” until you reach a simple answer.
Many recursion problems can also be done iteratively; choose what’s clearer and safer. 

Recursion template:
  Solve(n):
    if base_case(n) -> return answer
    else -> return Solve(smaller(n)) + extra_work
Example (Grey Box): Visualize the call stack
Each recursive call adds a frame; base case starts returning back up the stack. 
using System;

public static class RecursionIntro
{
    public static int SumToN(int n)
    {
        if (n <= 1) return n;           // base case
        return n + SumToN(n - 1);       // recursive case (smaller problem)
    }

    public static void Main()
    {
        Console.WriteLine(SumToN(5)); // 5+4+3+2+1 = 15
    }
}

Real-world use case

Recursion naturally fits hierarchical data like folders, org charts, and category trees—process node, then process children.

Safety reminder

If input can be very large (like 1,000,000), recursion may be risky; iterative solutions may be safer.

Beginner Tip

Always write the base case first, then write the recursive call.

Advanced Note

Some languages optimize tail recursion, but typical C# recursion is not guaranteed to be optimized—choose wisely.

10) Recursion Examples (Factorial, Fibonacci, Sum of Digits)

Practice recursion with classic interview-friendly problems

Factorial uses recursion because n! = n × (n−1)! until 1.
Fibonacci can be recursive, but naive recursion repeats work and becomes slow quickly.
Sum of digits reduces a number by splitting last digit + remaining digits.
Always confirm base cases and consider performance for large inputs.
For Fibonacci, iterative or memoized approaches are usually better in real apps. 

Three classic patterns:
  Factorial:    n! = n * (n-1)!
  Fibonacci:    F(n) = F(n-1) + F(n-2)
  SumDigits:    S(n) = (n % 10) + S(n / 10)
Example (Grey Box): Quick sanity tests
Factorial(5)=120, Fib(7)=13, SumDigits(947)=20 
using System;
using System.Collections.Generic;

public static class RecursionExamples
{
    public static long Factorial(int n)
    {
        if (n < 0) throw new ArgumentException("n must be >= 0");
        if (n <= 1) return 1;
        return n * Factorial(n - 1);
    }

    // Memoized Fibonacci (fast enough for reasonable n)
    private static readonly Dictionary _memo = new Dictionary { {0,0}, {1,1} };

    public static long Fibonacci(int n)
    {
        if (n < 0) throw new ArgumentException("n must be >= 0");
        if (_memo.ContainsKey(n)) return _memo[n];
        _memo[n] = Fibonacci(n - 1) + Fibonacci(n - 2);
        return _memo[n];
    }

    public static int SumOfDigits(int n)
    {
        n = Math.Abs(n);
        if (n < 10) return n;
        return (n % 10) + SumOfDigits(n / 10);
    }

    public static void Main()
    {
        Console.WriteLine(Factorial(5));
        Console.WriteLine(Fibonacci(7));
        Console.WriteLine(SumOfDigits(947));
    }
}

Real-world use case

Sum-of-digits logic appears in checksum-like validations and digit-based rules (e.g., simple fraud filters, ID checks).

Performance note

Fibonacci is a common interview trap: show recursion, then improve using memoization or iteration.

Beginner Tip

Draw the first few calls on paper; recursion becomes easy when you see the pattern shrinking.

Advanced Note

When recursion depth is unpredictable, consider iterative loops or explicit stacks for reliability.

FAQs

Common questions learners ask

1) Is return type part of a method signature?

FAQ

In C#, overload resolution uses method name + parameter types/order. Return type alone cannot distinguish overloads.

2) When should I use out instead of returning a tuple?

FAQ

Use out for Try-pattern APIs (success/failure + result). For general multi-values, a tuple or a small result type is often clearer.

3) Are optional parameters always better than overloads?

FAQ

Not always. Overloads can be clearer when defaults are not stable or when you want strict call shapes for correctness.

4) Why is naive Fibonacci recursion considered slow?

FAQ

It recomputes the same values many times (overlapping subproblems). Memoization or iteration avoids repeated work.

Interview Questions

Concept + practical answers

1) Explain static vs instance methods with an example.

Interview
Answer: Static methods don’t need object state and are called using the type name. Instance methods act on per-object state and are called using an object reference.

2) What is method overloading and what can cause ambiguity?

Interview
Answer: Overloading means same name with different parameter lists. Ambiguity can happen with null arguments, optional parameters, or overloads that are too similar.

3) When would you use ref, out, and in?

Interview
Answer: Use out for extra outputs (Try-pattern), ref to modify an existing variable from the caller, and in to pass large value types by reference as read-only.

4) What are the two mandatory parts of a recursive function?

Interview
Answer: A base case to stop recursion and a recursive case that reduces the problem size. Missing base case can cause stack overflow.

5) How would you improve Fibonacci recursion for production?

Interview
Answer: Use memoization (cache results) or switch to iteration to avoid repeated computations and improve time complexity.

Glossary (Tooltips)

Terms used with hover tooltips
Term Tooltip Description
.NET A developer platform for building apps (web, desktop, mobile, cloud). It includes tools, libraries, and runtimes. C# code commonly runs on the .NET runtime.
Method A named block of code that performs an action. Methods can accept inputs and return outputs. They help reuse and organize logic.
Parameter A variable in a method definition that receives input from the caller. Parameters define what data a method needs to do its job.
Overloading Having multiple methods with the same name but different parameter lists. It improves API usability but should be used carefully to avoid confusion.
static A keyword meaning the member belongs to the type itself, not to an instance. Static members are shared across all objects of that class.
params Allows a method to accept a variable number of arguments as an array. Useful for convenience APIs like Sum(params int[] numbers).
ref A modifier that passes a variable by reference so changes inside a method affect the caller’s variable. Use it when you must modify the original value.
out A modifier used to return additional values from a method. The method must assign it before returning. Common in TryParse patterns and multi-output methods.
in A modifier that passes by reference but treats the parameter as read-only inside the method. It can improve performance for large value types without allowing mutation.
Recursion A technique where a method calls itself to solve a problem. It must have a base case to stop, otherwise it can cause stack overflow.

1) Create a method to find the maximum of two integers

Easy
Problem: Write MaxOfTwo(a, b) that returns the larger number.
Input/Output: Input: two integers; Output: one integer (max).
Example Input/Output: Input: 7 12 → Output: 12
Constraints: a, b in range -10^9 to 10^9
Hint: Compare using if/else or Math.Max.

2) Write a method that converts minutes to seconds

Easy
Problem: ConvertMinutesToSeconds(minutes) returns minutes * 60.
Input/Output: Input: integer minutes; Output: integer seconds.
Example Input/Output: Input: 5 → Output: 300
Constraints: 0 ≤ minutes ≤ 10^7
Hint: Multiplication only; validate non-negative.

3) Create a method to count vowels in a string

Easy
Problem: CountVowels(text) returns number of vowels (a,e,i,o,u) ignoring case.
Input/Output: Input: string; Output: integer count.
Example Input/Output: Input: "Hello" → Output: 2
Constraints: 0 ≤ length ≤ 10^5
Hint: Convert to lowercase and check characters.

4) Make a method that returns true if a number is even

Easy
Problem: IsEven(n) returns true if n is divisible by 2.
Input/Output: Input: integer; Output: boolean.
Example Input/Output: Input: 14 → Output: true
Constraints: n in range -10^9 to 10^9
Hint: Use n % 2 == 0.

5) Create a method that reverses a string

Easy
Problem: ReverseText(text) returns the reversed string.
Input/Output: Input: string; Output: reversed string.
Example Input/Output: Input: "CSharp" → Output: "prahSC"
Constraints: 0 ≤ length ≤ 10^5
Hint: Convert to char array and reverse, or use a loop.

6) Create overloaded methods to calculate area (circle and rectangle)

Medium
Problem: Area(radius) returns circle area; Area(width, height) returns rectangle area.
Input/Output: Inputs: numbers; Output: double area.
Example Input/Output: Area(3) → 28.27 (approx), Area(4,5) → 20
Constraints: inputs ≥ 0
Hint: Use Math.PI for circle; overload by parameter count.

7) Build a method that uses optional parameters for discounts

Medium
Problem: FinalPrice(price, discountPercent = 0, taxPercent = 0) returns final amount.
Input/Output: Input: decimals; Output: decimal final price.
Example Input/Output: FinalPrice(100, discountPercent:10, taxPercent:18) → 106.20
Constraints: 0 ≤ percent ≤ 100, price ≥ 0
Hint: Apply discount first, then tax.

8) Use params to compute average of N integers

Medium
Problem: Average(params int[] nums) returns average as double; handle empty input.
Input/Output: Input: N integers; Output: double average (0 for none).
Example Input/Output: Average(2,4,6) → 4.0
Constraints: N up to 10^5
Hint: Sum in long; if count=0 return 0.

9) Implement TryParse-like method for positive decimal

Medium
Problem: TryReadPositiveDecimal(text, out value) returns true only if parsed and value > 0.
Input/Output: Input: string; Output: bool + out decimal value.
Example Input/Output: Input: "12.50" → true, value=12.50
Constraints: text length ≤ 10^5
Hint: Use decimal.TryParse then check > 0.

10) Write a method that swaps two integers using ref

Medium
Problem: Swap(ref a, ref b) exchanges values of a and b.
Input/Output: Input: two integers by reference; Output: swapped values (in caller).
Example Input/Output: a=3,b=9 → after Swap: a=9,b=3
Constraints: integers within -10^9..10^9
Hint: Use a temp variable.

Summary

What you should remember

Key takeaways

  • Method anatomy = name + return type + parameters; signature is mainly name + parameter list.
  • Static is for behavior without per-object state; instance methods work with object state.
  • Design clean APIs: small parameter lists, return results, use Try-pattern for safe parsing.
  • Overloading improves usability but avoid ambiguous overload sets.
  • Optional + named args improve readability; params supports variable inputs.
  • ref/out/in are powerful; use them with care for clarity and maintainability.
  • Recursion needs base case + recursive case; optimize when performance matters.
